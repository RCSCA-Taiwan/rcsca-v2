# 備份與還原驗證

## 已有工具

- `npm run backup:check`：只列出設定與工具是否存在，不顯示密碼、不連線、不建立備份。
- `npm run backup:create`：建立加密資料庫及 Storage 檔案備份；核對完整性與資料庫目錄後才寫入完成標記。
- `npm run backup:verify -- /absolute/backup-directory`：核對加密備份完整性，並不執行還原。
- `npm run verify:backup-restore`：在全新、無對外連線及無主機連接埠的 PostgreSQL 17 容器內，使用合成資料建立加密備份、還原至空白資料庫，再核對會員、點數餘額、外鍵、序號、RLS 與政策定義、Storage 原始檔案位元組。需要 Docker，不需要正式環境憑證。完成或失敗後移除容器、磁碟卷與暫存備份。

GitHub Actions 的 `backup-restore` 工作會獨立執行上述演練。請以該次工作的實際成功結果為準；存在腳本不等於通過驗證。

## 尚未完成的正式環境驗收

這個演練證明加密封裝與代表性資料可以還原，不是正式網站全量備份或 Supabase 託管服務完整還原演練。正式會員資料、圖片、權限及登入功能仍須在獨立復原環境驗收。

1. 指定備份執行位置、負責人、保留期間及獨立帳號／服務或受控離線保存位置。
2. 在受控執行位置提供專用資料庫連線及加密金鑰；有 Storage 檔案時需提供具讀取權限的伺服器端金鑰。不要把任何憑證貼進聊天、原始碼或公開環境變數。
3. 建立一次正式完整備份、核對完成標記、完成異地複製並再核對完整性；記錄實際時間與範圍。
4. 在獨立且不發送郵件的復原專案，依平台還原程序還原並逐項驗收。不要覆寫正式或共用測試資料庫。
5. 記錄實際復原時間、資料截止時間、缺失與負責人，通過後才啟用正式排程與定期演練。

現有邏輯備份使用 `--no-owner --no-privileges`，不包含角色擁有權、GRANT／REVOKE。RLS 政策定義會保留，但必須依版本化遷移與受控角色設定重建、核對權限；不能只檢查資料筆數。外部密鑰、Vault 解密金鑰、SMTP／Auth 供應商設定、網域與部署程式也需要另外復原；不要假設資料庫匯出能使這些設定直接恢復。Storage 資料表內的紀錄不能代替實際檔案，故演練會另外核對檔案內容。

正式設定尚未核對前，不把每日自動備份、異地備援或正式還原驗收標示為已完成。
