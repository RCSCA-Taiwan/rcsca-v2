真正做大之前，
先確保不會一次失去全部。

RCSCA 未來若累積會員、企業、活動、共享點與需求個案，最大的風險不是網站壞掉幾小時，而是帳號被接管、資料被刪除、敏感資料外洩，或沒有人知道怎麼復原。

四層安全原則

01 ACCOUNT

帳號不能共用

管理員、財務、會員管理、企業管理各自使用個人帳號，不使用「admin123」這類共用帳號。

02 ACCESS

最小必要權限

誰的工作需要什麼，就只開什麼。理監事、隊長、企業、工作人員不自動取得更多資料。

03 DATA

敏感資料分層

財務、PASS IT ON、身分驗證、特殊保護個案素材分開控管與記錄查閱。

04 RECOVERY

備份不是有做就算

備份必須能實際還原。至少定期做還原演練，不接受「我們應該有備份」這種狀態。

05 AUDIT

高風險操作留痕

刪除、合併帳號、調整點數、匯入資料、核發標章、查閱高敏感個案都要留紀錄。

06 OFFBOARD

離職／卸任立即撤權

人離開職務時，不等幾週後才處理。權限移除、金鑰更換、共用設備登出需有標準流程。

帳號管理規則

管理員一人一帳號禁止多人共用同一 Email／密碼，否則 Audit Log 沒有意義。
高權限帳號強制 MFA正式管理後台、雲端主機、資料庫、DNS、網域、GitHub 等都應使用多因素驗證。
Recovery Code 不放 LINE 群恢復碼與備援帳號應放在受控密碼管理器或離線安全位置。
權限每季檢查一次確認目前誰還需要後台、財務、個案、企業審核權限。
緊急 Super Admin 不做日常操作最高權限帳號平時不用來處理一般會員資料，只保留緊急與系統治理用途。

備份策略

每日

資料庫自動備份／快照。重大批次匯入、資料合併前再手動建立可回復點。

DB

每週

匯出關鍵結構化資料與設定摘要，存放在與正式資料庫不同的位置。

OFFSITE

每月

做一次抽樣還原測試，確認會員、企業、點數流水、個案資料能正確復原。

RESTORE TEST
原則：同一個雲端帳號裡的「另一份備份」不算完整異地備援。至少有一份關鍵備份放在不同帳號／不同服務或受控離線位置。

災難復原流程

01 發現網站異常、帳號被接管、資料錯刪或外洩。
02 隔離停用金鑰、凍結高風險帳號、暫停寫入。
03 評估確認影響範圍、時間點與涉及哪些資料。
04 還原從可信備份／版本回復，不直接在受感染環境硬修。
05 復盤更新權限、規則、金鑰與事故紀錄。

建議復原目標

系統可接受中斷可接受資料損失優先級
公開網站數小時幾乎無狀態資料中
登入／會員身份數小時不應遺失已完成驗證高

PASS IT ON 個案可短暫停機敏感資料不可遺失或錯置最高
企業標章／禮遇一天內可從紀錄重建中
生活分享內容一天內可接受小範圍損失低

高風險操作必須雙層核准

帳號合併

涉及共享點、會籍或身份衝突時，不能單人完成。

大量點數調整

單筆大量或批次更正，需要第二位管理者核准。

大量匯入／刪除

正式匯入前先建立回復點，執行後需驗證筆數與錯誤報表。

個案資料匯出

PASS IT ON 完整資料不得隨意下載 Excel；需理由、權限與查閱紀錄。

角色升級

任何人被提升為財務、個案、Super Admin 都需核准。

網域／DNS 變更

正式站 DNS、MX、驗證紀錄變更前需雙人確認，避免整站或 Email 中斷。

離職／卸任清單

立即移除帳號與角色後台、Supabase、Vercel、Cloudflare、GitHub、SMS Provider、密碼管理器。
撤銷 API Key／Token若曾由離任者接觸，重要 service key 直接輪替。
移轉企業／個案負責權不能因某人離職導致資料無人管理。
保留操作紀錄，不刪帳號歷史舊帳號停用即可，Audit Log 仍需知道過去是誰操作。
